Overview & Navigation

Micro DFIR is a single-appliance SOC platform combining SIEM, EDR, UEBA, SOAR, threat intel, and case management on one host. The left sidebar groups every feature area into its own page; most pages have their own sub-tabs (visible as a row of buttons near the top) rather than further nesting into the sidebar.

A few conventions apply across the whole app: destructive or high-impact actions (deleting a rule, purging logs, isolating a host) always show a confirmation dialog first. A stuck "Loading…" table with no data usually means a request failed — most tables show a red retry message instead these days, but if a page seems frozen, reloading is always safe.

Roles & Permissions

Access is controlled by roles (Settings > Security), each a named set of individual permission keys — not a fixed tier ladder. Three roles ship by default and can't be deleted, though their permissions can be edited:

RoleTypical scope
Tier 1/2 AnalystTriage, cases, basic EDR response actions.
Tier 3 Senior AnalystAdds hunting, detection tuning, and backend data access.
AdminEverything, including user/role management, system settings, and updates.

Admins can also create fully custom roles with any combination of permissions — useful for a narrowly-scoped role like an insider-threat investigator who needs UEBA and asset access but not system administration. A permission check happens server-side on every request; the sidebar and page controls simply hide what a role can't use.

Cases

A case tracks an investigation: linked alerts, UEBA anomalies, assets, tasks, notes, and a timeline of everything that happened. Two fields describe a case's state, and they mean different things:

  • Status (open/closed) — the administrative state of the case file.
  • Workflow state (new / investigating / awaiting input / resolved) — where the investigation itself stands.

Resolved means the technical investigation is done — the case may still be open administratively while paperwork or follow-up wraps up. Closed is the formal administrative close of the case file; closing a case automatically marks it resolved unless you set a different workflow state explicitly. A closed case can always be reopened if new evidence surfaces.

TLP (Traffic Light Protocol) and PAP (Permissible Actions Protocol) fields start unset ("not assessed") rather than defaulting to a specific classification — set them explicitly once you've actually assessed the case's sensitivity.

SIEM & Detection Rules

Detection rules are written in Sigma (the open, backend-agnostic detection-rule format) and compiled against this appliance's own SQLite-backed log store. Rules can be imported from the SigmaHQ community ruleset (whole release packs, or a picker to select individual rules), hand-authored via the guided rule builder, or edited directly as YAML.

Every rule carries a severity, and alerts it produces flow into the same triage queue as everything else. Rule Tuning lets you attach exclusions to a specific rule (e.g. "ignore this host") without touching the rule's own logic, and a false-positive triage action can suggest one for you, pre-filled from the alert you just triaged.

Log Search (a SIEM sub-tab) is the raw query interface into ingested logs — every other feature that needs to show "here's what actually happened" ultimately pulls from the same table this searches.

Log Pipeline

Controls what happens to a log between arriving at the appliance and landing in the searchable log store:

  • Drop Rules — discard noisy/unwanted events before they're ever stored, with a dry-run preview against real recent traffic before you commit to one.
  • DNS Query Logging — opt-in DNS query capture for hosts using this appliance as their resolver.
  • Windows / Linux Log Channels — which event log channels (Windows) or auditd rules (Linux) get pushed to agents, with optional per-agent-group overrides.
  • Silent Hosts — alerts when a previously-active host or log source has gone quiet.
  • Parsers — the field-extraction layer. Four built-in extractors always run (Windows Event XML, a Windows message-body regex fallback, Linux auditd, and the DNS query parser); admin-defined custom parsers fill gaps the built-ins don't cover, using named-group regex patterns. The parser editor shows a live preview of what a pattern would extract as you type it, and can pull a real recent log in to test against before you save.

EDR / Agents

Lightweight Windows/Linux/macOS agent scripts check in periodically and can be given response actions to run — queued from the Agents page and picked up on the endpoint's next check-in (usually within 15 seconds while online). Actions range from read-only collection (process list, network connections, browser history, software inventory) to active response (kill a process, isolate a host from the network, quarantine a file).

The most impactful actions — isolating a host, killing a process — require the edr.command.advanced permission; routine collection actions use the more widely-granted edr.command.basic. Automatic Endpoint Sweeps can run a bundle of safe, read-only checks (hash sweeps, YARA string sweeps, hardening checks, software inventory) on a schedule across every online endpoint, instead of only when queued by hand.

UEBA

User and Entity Behavior Analytics scores hosts and users on accumulated risk — failed logins, rare processes, threat-intel matches, anomalous timing, and more — each indicator contributing points toward an entity's overall risk score. Scoring weights are fully editable (UEBA > Scoring & Rules) rather than fixed. An entity whose score crosses a threshold can automatically open a case.

The Asset & Identity tab is where hosts get a criticality tier (standard/important/critical) — this feeds both UEBA's peer-group comparisons and general risk context elsewhere in the app.

SOAR (Playbooks)

Playbooks are trigger + action sequences: a trigger (case created, alert created, SLA breached, and others) fires a sequence of actions (apply a case template, send a notification, run an EDR action, and more). Some actions — anything that isolates a host or restores network access — always require human approval via the Pending Approvals queue, regardless of who built the playbook; this is a deliberate, non-configurable safety property.

Custom webhook actions let an admin define a reusable, named HTTP action (e.g. "Notify PagerDuty") without needing a code change for every new integration.

Coverage

Three related views of detection posture, as sub-tabs of the same page:

  • MITRE ATT&CK — which techniques have real, validated detection coverage vs. a gap, tracked over time.
  • Compliance — the same idea mapped onto compliance frameworks (e.g. PCI DSS, CIS Controls) instead of ATT&CK techniques.
  • Vulnerability — a live snapshot of known CVEs matched against each endpoint's installed software inventory.

Reports

Generates PDF reports (Security Summary, Compliance, Audit Trail, Vulnerability) on demand or on a recurring schedule, with three sub-tabs:

  • Reports — generate one now, browse history, download or email a past report.
  • Branding — company name, footer text, accent color, and an optional logo applied to every generated report.
  • Schedule — a recurring cadence (daily/weekly/monthly) per report type, with an optional email recipient list (uses the SMTP server configured under SOAR > Notification Channels).

Backup, Retention & Updates

Settings > System covers log retention (automatic purge of old logs past a configured age), log archiving (moving old logs to cold storage instead of deleting them), and database backups (scheduled or on-demand, with a configurable retention window on the backups themselves).

Settings > Changelog shows what version this appliance is running, checks GitHub for anything newer, and can pull and apply an update in place — the exact same process as running update.sh by hand, just triggered from the UI. An update briefly restarts the platform's services; your database and settings are always preserved.
